# Stintmate IPC

Stintmate IPC v2 is the protocol the Stintmate apps and connectors talk over: Windows named
pipes, MessagePack frames, an authenticated handshake with a per-user key file, calls,
events, state and stream channels. The protocol is defined in [`SPEC.md`](SPEC.md); the
byte-exact test vectors are in [`vectors/`](vectors/).

This repository holds the reference implementation, written in Rust, and its product: the
native library `stintmate_ipc.dll` with its header `crates/stintmate-ipc-ffi/include/stintmate_ipc.h`. Every language,
Python included, uses the DLL through the C ABI. This repository contains no Python package and
no examples.

| Path | What |
|---|---|
| `crates/stintmate-ipc/` | the core library (Rust API, async on Tokio, plus a blocking facade) |
| `crates/stintmate-ipc-ffi/` | the C ABI: `stintmate_ipc.dll`, header `include/stintmate_ipc.h` generated by cbindgen, MessagePack payloads |
| `crates/stintmate-ipc-check/` | `stintmate-ipc-check`, the conformance tool |

## Building

Requirements on Windows: Rust (the version in `rust-toolchain.toml`, installed by rustup) with
the MSVC target and the Visual Studio Build Tools C++ workload.

```
cargo build --release -p stintmate-ipc-ffi   # target/release/stintmate_ipc.dll
cargo build --workspace                      # also builds the DLL the FFI tests load
cargo test --workspace
```

The header is generated by the build and committed (`crates/stintmate-ipc-ffi/include/`).
The checks the `ci` and `release` workflows run also need `cargo fmt`, `cargo clippy` and
[`cargo-deny`](https://github.com/EmbarkStudios/cargo-deny) (`cargo install cargo-deny`).

The **workspace** that the key file and the endpoint registry live in is a per-user folder found
through `STINTMATE_WORKSPACE` or a pointer file (SPEC section 4.3). `list` and `keygen` without a path
fail with "no workspace" until one of them is set.

## The C ABI

The ABI is versioned apart from the crate (ABI 1.0, with crate 0.3.3): MAJOR changes on any
removal, rename, signature or meaning change; MINOR grows when functions, constants, struct
fields at the end or MessagePack map keys are added. A caller accepts a DLL with the same
MAJOR and a MINOR at least its own (`stintmate_ipc_abi_version()`). The rules (return codes,
buffer ownership, handles, callbacks and threads, `user_data` and `release`, structs with
`struct_size`, timeouts, panics, strings, shutdown) are the comment at the top of
[`stintmate_ipc.h`](crates/stintmate-ipc-ffi/include/stintmate_ipc.h). A test pins every
exported symbol and its signature (`crates/stintmate-ipc-ffi/tests/abi_baseline.txt`).

## The conformance checker

`stintmate-ipc-check` checks an implementation (client or server) against the protocol. Commands:
`server <pipe>`, `client <pipe>`, `list` (the workspace's endpoint registry) and `keygen [path]`;
`--help` prints every option. It exits 0 when every check passed, 1 when one failed, 2 on a usage error.

```
cargo run --release -p stintmate-ipc-check -- --help
```

## Releases

A release of tag `vX.Y.Z` carries four files (the assets of releases older than the newest
may have been removed; only the newest is guaranteed to have them):

| Asset | What it is |
|---|---|
| `stintmate_ipc.dll` | the native library with the C ABI |
| `stintmate-ipc-check.exe` | the conformance checker |
| `stintmate_ipc.h` | the C header of that DLL |
| `SHA256SUMS` | SHA-256 of the three files above, in `sha256sum` format; check with `sha256sum --check SHA256SUMS` |

The release notes are the version's section of [`CHANGELOG.md`](CHANGELOG.md). Tags with a
`+` suffix (`v0.3.1+docs.1`) mark documentation-only changes: they have no release and no assets.
The Python wheel is not part of these releases; it is published by the `stintmate-ipc-python`
repository.

To publish one, a maintainer runs the `release` workflow by hand (Actions, `release`, Run
workflow) with the `tag` to release (by convention from `main`; the workflow does not check which branch it was started from):

- The tag must exist, be an ancestor of `main`, equal `v` + the workspace version in
  `Cargo.toml`, and have its `## <version>` section in `CHANGELOG.md`. A tag with `+` is refused.
- The workflow builds the tag's tree (not `main`'s), runs the same checks as `ci` (fmt, clippy,
  build, test, cargo-deny), builds the release binaries with `--locked`, uploads the assets to a
  draft release, downloads them again and compares them with what it built.
- With `dry_run` (the default) it stops there: the draft is named `dry-run-<tag>` under the tag
  `dry-run-<version>`, the hashes are printed (next to those of the tag's published release, when
  there is one; rebuilt binaries need not be byte-identical), and the draft is deleted.
  Without it, the draft is published as the release of the tag. A tag that already has a published
  release is refused.

The logic that can run on its own is in `scripts/` (`release-check.sh`, `release-notes.sh`,
`release-sums.sh`, `release-report.sh`; bash, git and the GitHub CLI).
